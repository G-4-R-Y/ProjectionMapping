# Research sweep — 2026-09-14

This is the first dated research sweep for ProjectionMapping. Because there was no previous dated sweep, it establishes a baseline using projects published or materially updated during 2026, with emphasis on the last few months.

The promotion rule is conservative: a project can influence the roadmap freely, but it only enters the runtime automatically when licensing is clear, code is reproducible, scope is manageable, platform assumptions are explicit, and there is a deterministic test/smoke path.

## Executive summary

Three directions are especially relevant to the project right now:

1. **Structure-preserving streaming diffusion** is getting much closer to the exact M3/M4 problem. LiveEdit and LiveLight are more interesting to us than generic text-to-video because they preserve source structure while changing semantics or illumination over time.
2. **Open-source realtime visual tooling is improving quickly.** TiXL, OpenVJ, Ghost Arcade, and Vorce provide useful reference designs for graph-based control, WebGPU/WGPU rendering, mapping UX, MIDI/audio modulation, shader catalogs, and standalone compositor roles.
3. **Cross-platform GPU texture transport remains fragmented.** Spout is still Windows-centric and Syphon macOS-centric. rusty-syphon-spout is a useful MIT reference; Bucatini is technically promising for NDI bridging but was not promoted because its repository does not currently expose a clear project license.

No external project was vendored or added as a hard dependency in this sweep.

The code change promoted this month is internal: the feature registry can now declare required external executables, and the console can refuse launch with a clear `missing external command` message. This gives future integrations a safe, optional dependency model rather than assuming every VJ/transport tool is installed.

A cross-platform GitHub Actions matrix was also added for Ubuntu, Windows, and macOS on Python 3.10 and 3.12.

## 1. LiveEdit

Repository: <https://github.com/cp-cp/LiveEdit>

**Status:** high-priority research candidate; not integrated yet.

**License:** Apache-2.0.

**Recent activity:** inference/training code and checkpoints were released on 2026-06-24; long-video inference with rolling attention sinks and window-relative RoPE was added on 2026-08-05.

**What it does:** causal chunk-by-chunk diffusion-based streaming video editing with preservation of backgrounds and unchanged regions. It includes an AR-oriented mask cache that reuses computation in unchanged regions.

**Why it matters:** this maps directly to M3/M4. Our goal is not generic AI video; it is “change the material/semantics while keeping physical geometry stable.” LiveEdit's changed-region focus and streaming source preservation are therefore more relevant than unconstrained generation.

**Platform/runtime:** Linux + NVIDIA is the recommended path. The released setup uses Python 3.10, FlashAttention, Wan2.1, and a separate checkpoint. Single-GPU inference is supported, but no claim is made here about RTX 4080 performance.

**Next experiment:** isolate in its own environment/process and benchmark an input sequence from the room against the existing StreamDiffusion path. Measure structure retention, update latency, VRAM, and whether mask-cache behavior actually helps a mostly-static wall scene.

## 2. LiveLight

Repository: <https://github.com/mayuelala/LiveLight>

**Status:** high-priority M4/M5 candidate; not integrated yet.

**License:** MIT.

**Recent activity:** project/paper released 2026-07-24; code and weights released 2026-07-27.

**What it does:** realtime streaming video relighting with interactive 3D point-light position, intensity, and RGB color control. Its design uses geometry-guided feedback, few-step distillation, and a rolling temporal window.

**Reported performance:** the project reports 15.78 FPS and 0.253 s latency with its standard VAE; that number is not assumed to transfer to the RTX 4080 until measured locally.

**Why it matters:** room-skin does not need to be only “replace wall with moss.” Relighting the physical scene coherently is itself a powerful spatial illusion. More importantly, its geometry-guided feedback architecture is a useful reference for keeping generative changes locked to physical structure.

**Platform/runtime:** CUDA-enabled PyTorch; released requirements target PyTorch 2.1 and use a Python 3.10 environment. xformers is recommended.

**Next experiment:** use a short calibrated room capture and test whether synthetic point-light motion remains aligned with shelf/wall edges. If it does, expose light position/color as live control-deck parameters or OSC/MIDI channels.

## 3. LongLive 2.0

Repository: <https://github.com/airobotcode/longlive>

**Status:** M10 systems research reference.

**License:** Apache-2.0.

**Recent activity:** LongLive 2.0 released in May 2026, followed by additional KV-cache and RAG work in June 2026.

**Interesting ideas:** NVFP4 inference, quantized KV cache, attention sinks, sequence parallelism, async decoding, and long-stream autoregressive generation.

**Why it matters:** not as a direct dependency today, but as a source of techniques for our future long-running generative renderer. The important lesson is architectural: cache continuity, async decode, and explicit stream scheduling matter as much as nominal model FPS.

**Hardware caveat:** headline throughput is aimed at much larger modern datacenter GPUs. Do not plan the RTX 4080 runtime around these numbers.

## 4. Krea Realtime 14B

Repository: <https://github.com/krea-ai/realtime-video>

**Status:** research reference only; not suitable for automatic integration.

**License:** CC BY-NC-SA 4.0.

**System requirements:** Linux, Python 3.11+, and 40 GB+ VRAM recommended. The repository reports 11 FPS on an NVIDIA B200 using four inference steps.

**Why it matters:** useful source code for streaming server design, Self-Forcing-derived autoregressive video generation, KV-cache management, and WebSocket interaction.

**Why it is deferred:** the RTX 4080 does not meet the recommended VRAM target, and the non-commercial/share-alike license makes it a poor core dependency for a general project toolkit.

## 5. RDVFI

Repository: <https://github.com/Mayongrui/RDVFI>

**Status:** watch for code release.

**What is interesting:** RDVFI uses a latent diffusion model to produce sparse motion/keyframe information, then uses continuous pixel trajectories / optical-flow-style warping for high-resolution intermediate frames. The project reports realtime 1024x576 interpolation in the paper/project page.

**Why it matters:** this is almost exactly our hybrid philosophy: expensive neural inference should define semantic or motion state, while deterministic graphics/warping should carry the high-rate display loop.

**Why it is not integrated:** the current repository is effectively a project page and does not provide the implementation/evaluation code needed for a reproducible integration.

# Realtime mapping / compositor tools

## 6. TiXL

Repository: <https://github.com/tixl3d/tixl>

**Status:** strong standalone TouchDesigner-alternative experiment on Windows.

**License:** MIT.

**Activity/maturity:** actively updated in August 2026, with a substantial existing community/repository history.

**Architecture:** C#/DirectX realtime motion graphics with graph-based procedural content, timeline/keyframes, HLSL/compute shaders, MIDI/sensor inputs, OSC, and Spout.

**Why it matters:** M7 audio-latent performance and the high-rate procedural half of M3/M4 could potentially use TiXL as an external compositor. It also provides a mature UI reference for our own parameter exploration and graph concepts.

**Platform caveat:** DirectX makes this primarily a Windows path.

**Integration stance:** keep it as a standalone peer and communicate via Spout/OSC rather than importing its code.

## 7. OpenVJ

Repository: <https://github.com/kniessner/openvj>

**Status:** lightweight mapping/compositor candidate; watch/evaluate.

**License:** MIT.

**Created:** 2026-04-12. Repository metadata showed last push 2026-05-02 and update activity through August 2026.

**Architecture:** browser-based React + Three.js + WebGL projection mapping with quad warping, custom GLSL, p5.js, audio reactivity, MIDI control, and generative presets.

**Why it matters:** it is portable, simple to inspect, and could become a useful no-install-ish fallback mapping frontend or inspiration for a future web control surface.

**Maturity caveat:** the project identifies itself as beta and currently has a small contributor/user footprint.

---

## 8. Ghost Arcade

Repository: <https://github.com/riskcapital/ghost-arcade>

**Status:** technically compelling standalone peer; do not vendor.

**License:** AGPL-3.0-only.

**Capabilities:** WebGPU rendering, mesh/corner mapping, multi-output, MIDI, audio-reactive macros, large shader/effect catalog, 3D/point-cloud/Gaussian-splat content, and Spout I/O on Windows.

**Why it matters:** useful reference for the “infinite features with their own controls” direction of our console, especially effect metadata, macro/snapshot systems, ISF support, and modern GPU output.

**Why it stays external:** substantial functional overlap plus AGPL coupling make it better as a separate application than as copied/in-process code.

---

## 9. Vorce

Repository: <https://github.com/Vorce-Studios/Vorce>

**Status:** watch.

**License:** GPL-3.0.

**Architecture:** Rust + WGPU + Bevy, node-based realtime projection mapping, 3D/particle support, LUT grading, audio analysis, and NDI options.

**Why it matters:** WGPU/Bevy is an attractive cross-platform native rendering architecture and worth watching as the project matures.

**Why it is deferred:** currently early-stage/small compared with TiXL and our existing TouchDesigner path.

# Transport / shared-texture research

## 10. rusty-syphon-spout

Repository: <https://github.com/geepot/rusty-syphon-spout>

**Status:** good M2 native-sidecar reference.

**License:** MIT.

**Architecture:** Rust bindings around Syphon on macOS and Spout2 on Windows, including sender discovery and platform-specific runtime roundtrip tests. CI covers macOS and Windows.

**Why it matters:** our Python Spout adapter is intentionally lightweight and Windows-focused. A small native sidecar based on this pattern could eventually provide a cleaner Windows/macOS transport abstraction while keeping the Python UI/runtime independent.

**Why it is not integrated yet:** embedding a Rust build/toolchain into the core package is a larger dependency decision than this sweep should make. Revisit when macOS Syphon becomes a concrete requirement or when Python Spout bindings become a bottleneck.

---

## 11. Bucatini

Repository: <https://github.com/naporin0624/bucatini>

**Status:** technically relevant but blocked from auto-integration by licensing ambiguity.

**Architecture:** NDI input -> Syphon/Metal on macOS, Spout on Windows. The README states macOS has been hardware-verified; Windows is currently compile-verified in CI only and explicitly warns that color order, vertical flip, and SpoutDX details still need hardware testing.

**Why it matters:** it would make a useful network-ingest bridge for distributed inference or multi-machine experiments.

**Why it is deferred:** during this sweep no top-level LICENSE file or Cargo package license declaration was found. The README documents licenses for bundled/third-party components, but that is not enough to assume permission to integrate the project itself.
